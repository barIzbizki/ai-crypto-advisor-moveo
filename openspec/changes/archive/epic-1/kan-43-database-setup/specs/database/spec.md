## Purpose

Provides the backend's persistence foundation: a local Postgres instance, an application-level database connection/session lifecycle, and a version-controlled schema migration process that later features build their data models on top of.

## ADDED Requirements

### Requirement: Local Postgres Service
Developers SHALL be able to bring up a local Postgres instance for the backend with a single command, without installing Postgres on the host machine. The service's connection details (host, port, database name, credentials) SHALL be configurable via environment variables, and its data SHALL persist across container restarts.

#### Scenario: Starting the local database
- **WHEN** a developer runs the project's local database startup command
- **THEN** a Postgres instance becomes reachable on the configured host/port with the configured database and credentials already created

#### Scenario: Data persists across restarts
- **WHEN** the local Postgres container is stopped and started again without removing its volume
- **THEN** previously written data is still present

### Requirement: Application Database Connectivity
The backend application SHALL establish a database connection using a single configurable connection string (`DATABASE_URL`-style setting) and SHALL provide request-scoped database sessions to application code, ensuring each unit of work gets an isolated session that is properly closed when finished.

#### Scenario: Backend starts with a valid database configuration
- **WHEN** the backend application starts with a valid database connection string pointing at a reachable Postgres instance
- **THEN** the application starts successfully and can execute a trivial query (e.g. a connectivity check) against that database

#### Scenario: Backend fails fast with an invalid database configuration
- **WHEN** the backend application starts with a database connection string pointing at an unreachable database
- **THEN** attempting to use the database (e.g. a request that requires a session) surfaces a clear connection error rather than hanging indefinitely or silently succeeding

#### Scenario: Request-scoped session isolation
- **WHEN** two separate requests each obtain a database session
- **THEN** each request receives its own session instance, and one request's uncommitted changes are not visible to the other

### Requirement: Schema Migration Tooling
The project SHALL maintain database schema changes as version-controlled migration scripts, generated from the application's ORM model definitions, that can be applied to or rolled back from a target database in a repeatable, ordered fashion.

#### Scenario: Applying all migrations to a fresh database
- **WHEN** a developer runs the migration upgrade command against a fresh, empty Postgres database
- **THEN** all migrations apply successfully in order and the command exits with no error

#### Scenario: Rolling back migrations
- **WHEN** a developer runs the migration downgrade command back to the base revision on a database that has all migrations applied
- **THEN** the schema changes introduced by those migrations are reverted and the command exits with no error

#### Scenario: Detecting model/schema drift
- **WHEN** the ORM model definitions change and a developer requests an autogenerated migration
- **THEN** the migration tooling produces a migration script reflecting the difference between the current models and the database schema at the latest applied migration

### Requirement: Initial Baseline Migration
The project SHALL include an initial migration establishing the baseline schema state (empty, since no domain models exist yet), so that every environment's database history starts from the same known point.

#### Scenario: Fresh environment reaches a known baseline
- **WHEN** a new environment's database has the initial migration applied
- **THEN** its schema state matches the baseline defined by that migration, with no manual setup steps beyond running the migration command
