## Context

See proposal.md - Why. Relevant constraints: backend is FastAPI on Python 3.12 (`backend/pyproject.toml` targets `py312`), dependencies are currently pinned directly in `backend/requirements.txt`, and `backend/models/` exists only as an empty placeholder package from KAN-10. There is no `backend/core/config.py` yet — settings (if any) would need to be introduced as part of this change to hold `DATABASE_URL`.

## Goals / Non-Goals

**Goals:**
- A one-command local Postgres for development that any contributor can run without host-level Postgres install.
- A single, conventional SQLAlchemy engine/session/Base setup that later feature work (KAN-4 stories) can import models against.
- Alembic wired to autogenerate from the SQLAlchemy `Base.metadata`, with a working baseline migration.

**Non-Goals:**
- Defining any actual domain models (users, portfolios, AI insights, etc.) — that belongs to the features that need them.
- Production database provisioning/hosting (managed Postgres, backups, connection pooling at scale) — local dev only for this change.
- CI wiring to run migrations automatically — out of scope unless a later change requests it.

## Decisions

- **Postgres via `docker-compose.yml` at the repo root.** Keeps a single entrypoint (`docker compose up`) consistent with the repo's existing top-level layout (`/frontend`, `/backend`) rather than nesting compose config under `/backend`. Alternative considered: a Postgres install script — rejected, since it's host-OS-specific and harder to keep consistent across contributors.
- **SQLAlchemy 2.x with the declarative `Base` + `sessionmaker` pattern, exposed via a FastAPI `Depends(get_db)` generator.** This is the standard FastAPI+SQLAlchemy idiom, keeps sessions request-scoped, and is what Alembic's autogenerate expects to inspect. Alternative considered: an async engine (`asyncpg` + `AsyncSession`) — deferred, since nothing in the current codebase is async-DB-aware yet and it can be introduced later without changing the migration story.
- **`psycopg[binary]` (psycopg3) as the Postgres driver.** Actively maintained, binary wheels avoid local build toolchain issues on contributors' machines. `psycopg2-binary` was considered but psycopg3 is the forward-looking choice for new projects.
- **Settings via a small `backend/core/config.py` (e.g. `pydantic-settings` or plain `os.environ` reads) providing `DATABASE_URL`.** Needed because no settings module exists yet; keeping it minimal avoids over-building configuration infrastructure this change doesn't need.
- **Alembic configured for autogenerate against `Base.metadata`**, with `env.py` importing the same `Base` used by the SQLAlchemy setup, so future model additions can be autogenerated rather than hand-written.
- **Initial migration is an empty baseline** (no tables), since no domain models exist yet. This gives every environment a shared starting revision to build subsequent model migrations on top of, rather than the first real feature also having to invent the migration baseline.

## Risks / Trade-offs

- [Docker not installed/available on a contributor's machine] → Document the Docker requirement in the README alongside the existing setup instructions; this mirrors how the project already documents Node/Python prerequisites.
- [Empty baseline migration adds a small amount of ceremony before the first real model exists] → Accepted trade-off: it decouples "database plumbing works" (this change) from "first domain model" (future change), matching the KAN-43 subtask boundaries.
- [Local `DATABASE_URL` defaults committed to `docker-compose.yml`/`.env.example` could be mistaken for production credentials] → Use clearly non-production placeholder values and ensure any real `.env` stays gitignored (already covered by KAN-10's `.gitignore`).

## Migration Plan

Not applicable in the deploy/rollback sense — this change introduces the migration tooling itself rather than migrating existing data. Rollback of this change is simply removing the added files/dependencies; there is no production data at risk since no domain models exist yet.
